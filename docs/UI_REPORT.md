# TapMesh native macOS implementation

This report describes TapMesh's SwiftUI/AppKit workspace (`io.tapmesh.mac`). It was first written on 2026-11-05 and updated for the Developer Preview.

The Developer Preview adds the device groups and setup guidance, an AI Agents settings page, and per-device approval and pause controls. The earlier automated evidence below covers the versions identified there. The [qualification record](FINAL_QUALIFICATION.md) tracks checks for the Developer Preview.

## Scope and provenance

Implemented an original native SwiftUI/AppKit application from the sanitized `SPEC.md`, `TOOL_CONTRACTS.md`, `CORE_REVIEW_FINDINGS.md`, and the frozen API messages from the implementation coordinator. No original application assets, binary evidence, investigation directories, or internal architecture were read. The application uses system controls, SF Symbols, semantic colors, native lists, split views, settings, panels, commands, and sheets. Files are separated into app, views, store, services, and a testable core library.

## Implemented surfaces

- **Sidebar.** Your devices, Needs setup, Running simulators, and Other simulators group the iOS devices by readiness. Rows show the device kind and OS version when available. Other simulators starts collapsed and remembers the user's choice. The selected device keeps its checkmark while the user visits other pages. Apps and Builds act on that device. Saved Files, Activity, and Approvals span devices.
- **Status bar and toolbar.** The status bar says in plain words "Starting local services…", "Connected" or "Offline", then the last action, a small spinner while busy, and after a take-over "You have control" (with "· 1 request stopped" / "· N requests stopped"). The window's session ID and the last take-over's device ID, connection epoch, ownership generation and interrupted count appear only in the status bar tooltip; the device header has an info button whose "Technical details" popover shows device ID, connection epoch, take-control epoch, ownership generation and requests interrupted. Neither the status bar nor the header shows epoch/generation as text. The toolbar has Take Control, Stop Recording (only while recording), Reconnect, an "N Requests to Approve" button when requests wait, and Settings. A Device menu offers Refresh Devices (⇧⌘R), Refresh Screen (⌘R), Inspect Elements (⇧⌘I) and Home (⇧⌘H).
- **Device screen.** One control bar holds Home, Back, Rotate, Appearance, Type Text, Live, Refresh Screen, Save Screenshot, Record, and Inspector. As the window narrows, secondary labels disappear and Rotate, Appearance, and Save Screenshot move to More. A visible workspace uses refreshed screenshots until video plays. While live video plays, screenshots refresh the observation used for clicks and inspection every two seconds. Screen polling pauses when the window or device page is hidden. The setup card explains why a device isn't ready and offers a check or simulator start where available.
- **Tap and swipe feedback.** A click shows a short ring at the tapped point; a drag shows a line with start and end dots. If the store sent nothing for that action (out-of-date frame, busy, control changed, not connected, or a service error marked `not_sent`), the mark is replaced by a red X (dashed red line for a drag) for about a second. A transport failure keeps the ordinary mark because the action may have reached the device. With Reduce Motion the marks appear and disappear without scaling or fading. Marks are visual only and never hit-tested. The screen image, marks and coordinate math stay left-to-right in every language.
- **Inspector.** Closed by default; the choice is remembered across launches. It opens by itself when Inspect Elements returns a new snapshot. It has Elements and Capabilities tabs, a filter, Inspect Screen, separate Accessibility and text-recognition (OCR) source labels, a Tap button per element, and a context menu with Replace Text… and Copy Reference. When the screen may have changed the list is cleared with an explanation.
- **Element highlight.** The selected or hovered inspector row is outlined on the screen image only when `ElementHighlight` (TapMeshCore) proves the element snapshot and the displayed frame describe the same screen: same selected device and connection epoch for both, a snapshot ID, equal logical size and orientation, observation times within the snapshot's max age (at most 30 s), a usable image-to-device transform that covers exactly the logical screen, and element bounds that are a real area inside it. Otherwise nothing is drawn. The outline is never hit-tested or animated.
- **Type Text sheet.** The heading names the target device or the field selected in Inspector. The editor warns when the chosen field reference is stale. Paste explains that it replaces the device clipboard and may reach other Apple devices. On a physical device, confirm the US keyboard layout before typing and confirm the destination is a normal app field before either method. More Options contains Type, Paste, and Hide Device Keyboard. The confirmations reset when a takeover interrupts work. The same send rules apply to the button and ⌘Return. Physical input uses the selected text method and a fresh reference for replacement. It checks whether the phone is locked and leaves field selection to the user.
- **Apps.** The list loads automatically once per chosen device when the device is ready, nothing else is running and the catalog offers `list_apps`; Refresh Apps reloads it. Load problems are shown in the empty state, not a banner, and each empty state names its reason (not connected, device not ready, loading, none installed, another action running, not loaded). Install App… opens a file panel for an .app or .ipa. Dropping an .app or .ipa on the list asks for confirmation first, and installs only on the device it was dropped on. More Options holds launch by bundle ID and install from a typed path. Each row has Launch and a menu with Terminate App and Uninstall App…, which confirms that the app's data is deleted.
- **Builds.** Project or workspace, scheme, configuration and "Launch after installation" are remembered across launches. Build and Run, or Cancel Build while running. The last build of the session stays on the page across page switches: device and start time, progress, then a plain headline (succeeded, partly finished, failed at a named step, cancelled, no result) and one row per returned stage with a succeeded/failed/other mark, the app bundle ID, a note that the log is in Artifacts, and the raw result under "Full result". If the stages can't be read, only the raw result is shown.
- **Activity.** Up to 300 entries for this session, newest first, each with a readable action name, a plain status, the time and a message. Actions that change a device carry a delivery note ("Nothing was sent to the device.", "The action did reach the device.", or "may have reached the device. Check it before retrying."), shown with a warning icon when delivery is uncertain. Error code, request ID and technical details are in small selectable text. Arguments and typed text are still never logged. A Clear button empties the list.
- **Approvals.** A new physical device gets one consent card when an AI client tries ordinary fast control. The card explains what a device grant permits and offers Allow and Deny. Specific actions show their argument summary and Allow Once. Protected steps ask the person to finish the step on the device. A banner above the preview shows recent agent control, with Stop while active and Resume while paused.
- **Approval notifications and Dock badge.** Approvals are read every 5 seconds, also in the background. When TapMesh is not in front, a new request from another session (or a hand-off from this window) produces at most one system notification per check, naming only the action and device. Notifications have no Allow/Deny buttons; clicking one brings TapMesh forward on the Approvals page, reopening the window if needed. Permission is asked the first time a notification is actually needed. The Dock icon always shows the number of waiting requests. Settings → General → Approvals has "Notify me when a request needs approval" (default on) and, if macOS notifications are off for TapMesh, a button to open Notification Settings. Notifications are skipped outside a real app bundle (for example `swift run`).
- **Saved Files.** The page shows usage for the coordinator's saved copies. Delete All Saved Files… asks for confirmation and clears both service stores. Select an image, recording, or text file for a preview. Large files load on request. Quick Look and Save a Copy… are available for individual items. Downloads stream to temporary files.
- **Tool Catalog.** Unchanged in purpose: schema-derived argument forms and a validated JSON editor for every catalog tool, showing schema, policy, capability state and the returned envelope. The server remains authoritative for validation and policy.
- **Settings.** General contains connection, language, device grants, and approval notifications. AI Agents gives the MCP configuration and Claude Code command with the install path filled in. The welcome page and Help menu open the same tab. Build Folders manages allowed projects. Advanced manages a custom connection. Diagnostics shows health, Apple tool availability, and the diagnostic export. About links to licenses and source. Language changes take effect after restart. The app keeps the bundled approval credential in memory.
- Standard keyboard shortcuts, VoiceOver labels and hints on screen and control inputs, native keyboard navigation, and Light/Dark adaptive styling. The only animation (tap marks) honours Reduce Motion.

## Localization

English text in the code is the localization key; English needs no strings file. Arabic lives in `macos/Localization/ar.lproj/Localizable.strings` (plus `InfoPlist.strings` for the local-network usage text). Strings are added as fragments in `macos/Localization/fragments/*.strings` and merged into `ar.lproj/Localizable.strings`; rules are in `macos/Localization/AGENT_BRIEF.md` and wording in `macos/Localization/GLOSSARY.md`. `scripts/package_app.py` copies every `macos/Localization/*.lproj` into `Contents/Resources` and sets `CFBundleDevelopmentRegion` to `en` and `CFBundleLocalizations` to `en`, `ar`. Service messages, device and file names, identifiers, paths and JSON stay as given and left-to-right. The automated first-launch check still relies on the English labels "Connected", "Your devices, within reach" and "Apps".

Known service error codes have localized recovery text. Technical strings such as device identifiers, paths, and MCP snippets stay selectable and left to right. Visual checks of Arabic mirroring, truncation, and sheet and toolbar widths remain pending for the release build.

## Local authorization behavior

Live checks of this behavior remain pending for the release build.

The UI creates its own UUID session and registers it through the settings endpoint. Native tool calls and approvals carry the service bearer and the private `X-DeviceBridge-Local-Authorization` bearer. The app keeps the bundled approval credential in memory. MCP only uses the service credential. The default configuration lives in `~/Library/Application Support/TapMesh/Local/connection.json`, with loopback HTTP URLs for both services.

An explicit local button or confirmed catalog action may authorize the approval ID returned for that identical request. This requires `approval_required`, `side_effect_state=not_sent`, and a matching session, tool, device, and connection epoch. Policy A device grants and policy U handoffs require an explicit decision. The UI allows the matching exact-action request and repeats the unchanged arguments once. After uncertain delivery it asks the person to inspect the device.

Take Control posts only `{session_id, device_id}` to `/api/takeover` with both the ordinary server bearer and private local owner header. The request builder rejects missing owner credentials and nonlocal/invalid configuration before network dispatch. No takeover tool is exposed to models. Receipts must confirm the requested device and include nonnegative integer connection epoch, ownership generation, and interrupted-request count.

If takeover interrupted work or changed the connection epoch, the UI discards old frames and element references and aborts the pending screen-bound action without replaying or rebinding its coordinates, refs, or focused text. Later quiet takeovers do not remove this fresh-screen requirement. A screenshot started after the current takeover, matching its device, epoch and generation, clears the gate; pre-takeover captures are discarded. A quiet takeover preserves the requesting owner's otherwise valid observations, matching the agreed server contract. Ownership checks around local approval/retry prevent an older UI request from reviving after a newer takeover. These metadata indicate control/cancellation outcomes rather than application business success.

## Integration gates and limitations

The UI worker did not launch or package the application. The parent owns runtime startup, application bundle/signing, and CUA visual/live integration inspection. No claim is made here that simulator/physical/backend operations passed live tests. Unsupported or missing prerequisites are surfaced from the service and capability profiles. The reworked UI, the approval notifications and the Arabic localization have not been visually or live qualified.

The frozen HTTP API has no separate progress stream or explicit cancel endpoint. Build progress is indeterminate until stage results return. Cancel Build cancels the HTTP task. The core worker verified socket-disconnect cancellation propagation through both real HTTP listeners (server and agent); this is coordinator-supplied integration evidence, not a live test performed by the UI worker. A device action delivered before cancellation may already have completed, so the UI instructs the user to inspect the result and device before retrying. Public distribution still needs signing, notarization, and clean-Mac qualification.

Activity and the last build show work from this app session. The coordinator keeps a bounded request history for coordination and diagnostics. The schema form supports scalar, enum, array, and object fields. The JSON editor handles alternative and nested shapes, and local validation provides feedback before sending.
